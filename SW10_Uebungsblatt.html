01 Erste Scripts und Variablen

Shebang, Variablen, Command Substitution, interaktive Eingabe.

A1

System-Übersicht

sysinfo.sh
  • Das Script gibt vier Informationen über das System aus, jeweils mit Beschriftung:
    • den Hostnamen
    • den aktuell angemeldeten Benutzer
    • das heutige Datum im Format 21.11.2026
    • wie lange das System schon läuft
  • Hostname, Datum und Laufzeit werden vorher in Variablen gespeichert
  • Der Benutzer wird über eine bereits existierende Umgebungsvariable geholt
  • Das Script heisst sysinfo.sh
Erwarteter Output
Hostname: ivan-sw04-instance
Benutzer: debian
Datum:    21.11.2026
Laufzeit: up 3 hours, 12 minutes
Tipp

Drei Befehle, die du brauchst: hostname, date und uptime. Probier sie zuerst einzeln im Terminal aus.

Für das Datumsformat: date --help zeigt die Platzhalter. Du brauchst Tag, Monat, Jahr, getrennt durch Punkte.

Für die Laufzeit hat uptime einen Schalter, der die Ausgabe auf „pretty" kürzt.

Den Benutzer musst du nicht ermitteln — die Variable gibt es schon, du hast sie bei env-vars.sh benutzt.

Lösung 
#!/bin/bash

HOST=$(hostname)
DATUM=$(date +%d.%m.%Y)
LAUFZEIT=$(uptime -p)

echo "Hostname: $HOST"
echo "Benutzer: $USER"
echo "Datum:    $DATUM"
echo "Laufzeit: $LAUFZEIT"

Merke: HOST=hostname würde die acht Buchstaben speichern. Nur $( ) führt den Befehl aus und setzt dessen Ausgabe ein.

A2

Altersrechner

age.sh
  • Das Script fragt interaktiv zwei Dinge ab:
    • den Namen des Benutzers
    • sein Geburtsjahr
  • Aus dem aktuellen Jahr und dem Geburtsjahr wird das Alter berechnet
  • Ausgegeben wird ein Satz mit Name und Alter
  • Das Script heisst age.sh
Erwarteter Output
Wie heisst du? Ivan
Geburtsjahr? 2002
Hallo Ivan, du wirst dieses Jahr 24.
Tipp

Abfragen geht mit read -p — der Text in Anführungszeichen, danach der Variablenname ohne $.

Das aktuelle Jahr bekommst du wieder mit date und dem passenden Platzhalter.

Rechnen geht in der Bash nicht einfach mit -. Du brauchst doppelte runde Klammern.

Lösung 
#!/bin/bash

read -p "Wie heisst du? " NAME
read -p "Geburtsjahr? " JAHR

JETZT=$(date +%Y)
ALTER=$(( JETZT - JAHR ))

echo "Hallo $NAME, du wirst dieses Jahr $ALTER."

Drei Klammerarten, drei Zwecke: $( ) führt einen Befehl aus, $(( )) rechnet, [ ] prüft eine Bedingung.

A3

Kopieren mit Parametern

copyfile.sh
  • Folgende Parameter werden dem Benutzer mit kurzer Beschreibung ausgegeben:
    • $0 – Script-Name
    • $# – Anzahl der Parameter
    • $1 – Quelldatei
    • $2 – Zieldatei
    • $* – alle Parameter zusammen
  • Parameter Nr. 1 ist die Quelldatei, Parameter Nr. 2 die Zieldatei
  • Danach kopiert das Script die Quelle auf das Ziel
  • Das Script heisst copyfile.sh
Erwarteter Output
$ ./copyfile.sh sysinfo.sh backup.sh
Script-Name: ./copyfile.sh
Anzahl Parameter: 2
Quelle: sysinfo.sh
Ziel: backup.sh
Alle Parameter: sysinfo.sh backup.sh
=== Kopiere ===
Fertig.
Tipp

Hier wird nichts gefragt — kein read. Die Werte gibt der Benutzer beim Start mit, hinter dem Script-Namen.

$0, $# und $* füllt die Bash automatisch. Du kannst sie nur lesen, nicht setzen.

Beim Kopieren die Variablen in Anführungszeichen setzen — Dateinamen können Leerzeichen enthalten.

Lösung 
#!/bin/bash

echo "Script-Name: $0"
echo "Anzahl Parameter: $#"
echo "Quelle: $1"
echo "Ziel: $2"
echo "Alle Parameter: $*"
echo "=== Kopiere ==="

cp "$1" "$2"
echo "Fertig."

Typische Falle: Bei $# kommt eine Anzahl heraus (hier 2), bei $1 ein Inhalt. Wer die beiden verwechselt, kopiert plötzlich eine Datei namens „2".

02 Verzweigungen und Test-Bedingungen

if, Exit-Codes, Dateitests, case.

A4

Plattenplatz-Warnung

disk-alert.sh
  • Als Parameter Nr. 1 nimmt das Script einen Schwellenwert in Prozent entgegen
  • Wird kein Parameter übergeben, gibt das Script eine Fehlermeldung aus und beendet sich
    • Nutzen Sie die Variable $# um die Anzahl der Parameter abzufragen
  • Das Script ermittelt die aktuelle Belegung des Dateisystems / in Prozent und gibt sie aus
  • Liegt die Belegung über dem Schwellenwert, wird eine Warnung ausgegeben, sonst eine Entwarnung
  • Das Script heisst disk-alert.sh
Erwarteter Output
$ ./disk-alert.sh 80
Belegung von /: 14%
Alles im grünen Bereich.

$ ./disk-alert.sh
[Error] Bitte einen Schwellenwert in Prozent angeben
Benutzung: ./disk-alert.sh <zahl>
Tipp

Die Belegung liefert df. Tipp sie zuerst einzeln ein: df -h /. Du bekommst zwei Zeilen und mehrere Spalten — du brauchst genau eine Zahl.

Die Kopfzeile wegschneiden: tail -n 1. Die richtige Spalte holen: awk '{print $5}'. Das Prozentzeichen entfernen: tr -d '%'. Alles mit Pipes aneinanderhängen.

Das Prozentzeichen muss weg, weil [ ] nur mit Zahlen vergleichen kann — 14% ist für die Bash Text.

Für „grösser als" schau in man test.

Lösung 
#!/bin/bash

if [ $# -eq 0 ]; then
    echo "[Error] Bitte einen Schwellenwert in Prozent angeben"
    echo "Benutzung: ./disk-alert.sh <zahl>"
    exit 1
fi

GRENZE=$1
BELEGT=$(df -h / | tail -n 1 | awk '{print $5}' | tr -d '%')

echo "Belegung von /: ${BELEGT}%"

if [ "$BELEGT" -gt "$GRENZE" ]; then
    echo "WARNUNG: Belegung über ${GRENZE}%!"
else
    echo "Alles im grünen Bereich."
fi

Die Pipe-Kette ist der Kern: alles holen → richtige Zeile → richtige Spalte → Zeichen weg. Übrig bleibt eine nackte Zahl, mit der man vergleichen kann. Genau das Muster aus dem Monitoring-Script.

A5

Ordner prüfen

dir-check.sh
  • Ordner zur Prüfung als Parameter Nr. 1 übergeben, ansonsten Fehlermeldung ausgeben
  • Prüfen ob es sich wirklich um ein Verzeichnis handelt
  • Falls ja:
    • Prüfen ob lesbar und Ergebnis ausgeben
    • Prüfen ob beschreibbar und Ergebnis ausgeben
    • Anzahl der enthaltenen Einträge ausgeben
  • Das Script heisst dir-check.sh
Erwarteter Output
$ ./dir-check.sh /etc
Verzeichnis existiert.
Verzeichnis lesbar.
Verzeichnis nicht beschreibbar.
Enthält 142 Einträge.
Tipp

Für „ist ein Verzeichnis" gibt es ein eigenes Kürzel — -e wäre zu unscharf, das trifft auch auf Dateien zu. Schau in man test bei den Dateitests.

Die drei Prüfungen gehören in den Verzeichnis-Block hinein („Falls ja"), sonst melden sie Unsinn, wenn der Ordner gar nicht existiert.

Einträge zählen: ls -1 ordner | wc -l. Das -1 ist eine Eins und erzwingt eine Zeile pro Eintrag.

Lösung 
#!/bin/bash

if [ $# -eq 1 ]; then

    if [ -d "$1" ]; then
        echo "Verzeichnis existiert."

        if [ -r "$1" ]; then
            echo "Verzeichnis lesbar."
        else
            echo "Verzeichnis nicht lesbar."
        fi

        if [ -w "$1" ]; then
            echo "Verzeichnis beschreibbar."
        else
            echo "Verzeichnis nicht beschreibbar."
        fi

        ANZAHL=$(ls -1 "$1" | wc -l)
        echo "Enthält $ANZAHL Einträge."

    else
        echo "Das ist kein Verzeichnis."
    fi

else
    echo "[Error] Bitte genau einen Ordner angeben."
    exit 1
fi

Dateitests im Überblick: -e existiert · -f normale Datei · -d Verzeichnis · -r lesbar · -w beschreibbar · -x ausführbar. Die letzten drei sind dieselben Buchstaben wie bei chmod.

A6

Netzwerk-Menü

netmenu.sh
  • Eine Menüauswahl mit Punkten und zugehöriger Zahl wird dem Benutzer ausgegeben
  • Interaktiv wird die Auswahl eines Menüpunkts angefordert
  • Folgende Menüpunkte sollen zur Verfügung stehen:
    • Ausgabe der IP-Adressen des Systems
    • Ausgabe der offenen Ports
    • Ausgabe des Standard-Gateways
    • Ein Menüpunkt zum Beenden
  • Bei einer ungültigen Eingabe gibt das Script einen Fehler aus und beendet sich
  • Das Script heisst netmenu.sh
Erwarteter Output
=== Netzwerk-Menü ===
1) IP-Adressen
2) Offene Ports
3) Standard-Gateway
4) Beenden

Ihre Wahl (1-4): 1
--- IP-Adressen ---
lo    UNKNOWN  127.0.0.1/8
ens3  UP       10.0.0.42/24
Tipp

Drei Befehle, alle vorinstalliert: ip für Adressen und Routen, ss für Ports.

  • IP-Adressen: ip mit dem Unterbefehl für Adressen. Mit -brief wird es übersichtlich.
  • Offene Ports: ss -tuln
  • Gateway: ip route, und davon die Zeile mit default herausfiltern

Jeder Fall im case endet mit ;; — das wird gerne vergessen.

Lösung 
#!/bin/bash

echo "=== Netzwerk-Menü ==="
echo "1) IP-Adressen"
echo "2) Offene Ports"
echo "3) Standard-Gateway"
echo "4) Beenden"
echo ""

read -p "Ihre Wahl (1-4): " WAHL

case $WAHL in
    1)
        echo "--- IP-Adressen ---"
        ip -brief address
        ;;
    2)
        echo "--- Offene Ports ---"
        ss -tuln
        ;;
    3)
        echo "--- Standard-Gateway ---"
        ip route | grep default
        ;;
    4)
        echo "Beendet."
        exit 0
        ;;
    *)
        echo "[Error] Ungültige Eingabe: $WAHL"
        exit 1
        ;;
esac

case vs. if: case nimmt man, wenn dieselbe Variable gegen mehrere Werte geprüft wird. Für mehrere verschiedene Fragen nimmt man getrennte if-Blöcke.

03 Schleifen und Iteration

for über Dateien und Listen, while mit Bedingung.

A7

Konfigurationsdateien prüfen

check_conf.sh
  • Iteration über eine Liste von Dateien mittels for-Schleife
    • Zielverzeichnis: /etc/*.conf
  • Prüfen der Leseberechtigung für den aktuellen Benutzer
  • Ausgabe ob die jeweilige Datei lesbar ist oder nicht
  • Bei lesbaren Dateien zusätzlich die Dateigrösse ausgeben
  • Das Script heisst check_conf.sh
Erwarteter Output
Benutzer: debian

Prüfe Datei: /etc/adduser.conf
  Lesbar — Grösse: 3.0K
Prüfe Datei: /etc/ca-certificates.conf
  Lesbar — Grösse: 6.0K
Prüfe Datei: /etc/sudo.conf
  Nicht lesbar
[...]
Tipp

Die for-Zeile hat genau drei Teile: Variablenname, in, Liste. Der Name steht ohne $ — du vergibst ihn ja gerade.

Das * im Pfad ist ein Glob: Die Bash setzt dort automatisch alle passenden Dateien ein.

Die Dateigrösse: du -h datei gibt Grösse und Pfad zurück. Nur die Grösse bekommst du mit cut -f1.

Lösung 
#!/bin/bash

echo "Benutzer: ${USER}"
echo ""

for FILE in /etc/*.conf; do
    echo "Prüfe Datei: $FILE"

    if [ -r "$FILE" ]; then
        GROESSE=$(du -h "$FILE" | cut -f1)
        echo "  Lesbar — Grösse: $GROESSE"
    else
        echo "  Nicht lesbar"
    fi
done

Zwei Klassiker hier: In der for-Zeile $FILE statt FILE schreiben (gibt not a valid identifier), und die Prüfung verdreht als [ "$FILE" -r ] — bei Dateitests kommt immer zuerst das Kürzel.

A8

Ports prüfen

check_ports.sh
  • Hinterlegen Sie die folgende Liste an Ports als Variable in Ihrem Script: 22 80 443 3306
  • Prüfen jedes Ports in der Liste mit einer for-Schleife
    • for erlaubt das Iterieren über eine Liste von Space-separated Strings mit in
  • Ausgabe ob auf dem jeweiligen Port etwas lauscht oder nicht
    • Sie können dies über den Exit-Code des Kommandos ss -tuln | grep -q ":<port> " abfragen
  • Das Script heisst check_ports.sh
Erwarteter Output
Prüfe Port: 22
  Port 22 ist offen
Prüfe Port: 80
  Port 80 ist offen
Prüfe Port: 443
  Port 443 ist geschlossen
Prüfe Port: 3306
  Port 3306 ist geschlossen
Tipp

Eine Variable, vier Werte: PORTS="22 80 443 3306". Das ist ein einziger Text mit vier Wörtern.

In der for-Zeile schreibst du $PORTS ohne Anführungszeichen — mit wäre es ein einziges langes Wort und die Schleife liefe nur einmal. Das ist die eine Stelle, wo die übliche Quoting-Regel umgekehrt gilt.

Das if braucht hier keine eckigen Klammern. Nach if darf jeder Befehl stehen — die Bash schaut auf seinen Exit-Code. grep -q gibt nichts aus und liefert 0, wenn es etwas gefunden hat.

Lösung 
#!/bin/bash

PORTS="22 80 443 3306"

for PORT in $PORTS; do
    echo "Prüfe Port: $PORT"

    if ss -tuln | grep -q ":$PORT "; then
        echo "  Port $PORT ist offen"
    else
        echo "  Port $PORT ist geschlossen"
    fi
done

Der Kern: [ ] ist selber nur ein Programm. Darum darf nach if jeder Befehl stehen. Exit-Code 0 = wahr, alles andere = falsch. Genau wie bei systemctl is-active --quiet.

A9

Stoppuhr

timer.sh
  • Das Script zählt von 1 bis zu einem Zielwert hoch und wartet dazwischen jeweils eine Sekunde
  • Der Zielwert kann als Parameter übergeben werden; ohne Parameter sind es 5 Sekunden
  • Die verbleibende Zeit wird in einer while-Schleife ausgegeben
    • Schauen Sie in man test für die Bedingung der Schleife
  • Am Ende wird eine Schlussmeldung ausgegeben
  • Das Script heisst timer.sh
Erwarteter Output
$ ./timer.sh 3
Stoppuhr läuft für 3 Sekunden...
Sekunde 1 von 3
Sekunde 2 von 3
Sekunde 3 von 3
Zeit abgelaufen!
Tipp

Du brauchst zwei Variablen: den Zielwert (aus $1) und einen Zähler, der bei 1 startet.

Für den Standardwert gibt es eine Kurzform: ${1:-5} heisst „nimm $1, und falls leer, nimm 5".

Die Bedingung lautet diesmal „kleiner oder gleich" — in man test steht das Kürzel dafür.

Hochzählen: I=$(( I + 1 )). Und sleep 1 nicht vergessen, sonst rauscht es durch.

Lösung 
#!/bin/bash

ZIEL=${1:-5}
I=1

echo "Stoppuhr läuft für $ZIEL Sekunden..."

while [ $I -le $ZIEL ]; do
    echo "Sekunde $I von $ZIEL"
    I=$(( I + 1 ))
    sleep 1
done

echo "Zeit abgelaufen!"

Achtung: > und < bedeuten in [ ] nicht grösser/kleiner, sondern Umleitung. Die Bash legt dir sonst stillschweigend eine Datei an. Für Zahlen immer -lt -le -gt -ge -eq -ne.

04 Funktionen und Debugging

Eigene Befehle bauen, Werte zurückgeben, Fehler finden.

A10

Temperatur-Umrechner

convert.sh
  • Der Umrechner soll zwischen Celsius und Fahrenheit umrechnen
  • Das Script nimmt die folgenden Parameter entgegen:
    • $1 – der Zahlenwert
    • $2 – die Richtung als String (CTOF oder FTOC)
  • Das Script soll zwei Funktionen beinhalten:
    • c_to_f bekommt eine Zahl als Parameter und gibt Grad Fahrenheit zurück
    • f_to_c bekommt eine Zahl als Parameter und gibt Grad Celsius zurück
  • Werden weniger als zwei Parameter übergeben, gibt das Script eine Fehlermeldung aus
  • Entscheide via case welche Funktion ausgeführt wird
  • Das Script heisst convert.sh
Erwarteter Output
$ ./convert.sh 20 CTOF
68 Grad Fahrenheit

$ ./convert.sh 68 FTOC
20 Grad Celsius
Tipp

Die Formeln: F = C * 9 / 5 + 32 und C = (F - 32) * 5 / 9. Die Bash rechnet nur mit ganzen Zahlen — das ist hier in Ordnung.

Wichtig: Innerhalb einer Funktion ist $1 der erste Parameter der Funktion, nicht der des Scripts. Du gibst ihr nur eine Zahl mit, also heisst die drinnen $1.

Die Funktionen rechnen nur — kein if, kein case darin. Die Entscheidung trifft das case draussen.

return taugt nicht für Ergebnisse, nur für Exit-Codes. Werte kommen mit echo heraus.

Lösung 
#!/bin/bash

# Funktion: Celsius nach Fahrenheit
c_to_f() {
    echo $(( $1 * 9 / 5 + 32 ))
}

# Funktion: Fahrenheit nach Celsius
f_to_c() {
    echo $(( ($1 - 32) * 5 / 9 ))
}

# Parameterprüfung
if [ "$#" -lt 2 ]; then
    echo "[Error] Zu wenige Parameter erhalten"
    echo "Benutzung: ./convert.sh <zahl> <CTOF|FTOC>"
    exit 1
fi

case "$2" in
    CTOF)
        echo "$(c_to_f $1) Grad Fahrenheit"
        ;;
    FTOC)
        echo "$(f_to_c $1) Grad Celsius"
        ;;
    *)
        echo "[Error] Ungültige Richtung: $2"
        echo "Erlaubt: CTOF oder FTOC"
        exit 1
        ;;
esac

Zwei getrennte Welten: Bei ./convert.sh 20 CTOF ist draussen $2 = CTOF. Beim Aufruf c_to_f 20 gibt es drinnen nur $1 = 20 — ein $2 existiert dort gar nicht. Die Funktion ist ein eigenes kleines Script.

Zur Erinnerung: Die Definitionen müssen vor dem Aufruf stehen. Die Bash liest von oben nach unten.

A11

Fehlersuche

broken.sh
  • Legen Sie das folgende Script als broken.sh an. Es enthält vier Fehler.
  • Finden Sie die Fehler — zuerst durch Nachdenken, dann mit bash -x broken.sh google.ch
  • Korrigieren Sie das Script, bis es funktioniert
#!/bin/bash

ANZAHL = 3
ZIEL=$2

if [$# -eq 0]
    echo "Kein Ziel angegeben"
    exit 1
fi

ping -c $ZIEL $ANZAHL
Tipp

Arbeite die Fehlermeldungen von oben nach unten ab — die Bash meldet immer nur den ersten.

Drei der vier Fehler hast du in dieser Übung selber schon mal gemacht. Achte auf: Leerzeichen, $-Zeichen, fehlende Schlüsselwörter und die Reihenfolge von Argumenten.

Der vierte Fehler erzeugt keine Fehlermeldung — das Script läuft, macht aber das Falsche. Diese Sorte findest du nur mit bash -x.

Lösung

Die vier Fehler:

  • ANZAHL = 3 → beim Zuweisen dürfen keine Leerzeichen ums = stehen. Die Bash hält ANZAHL sonst für einen Befehl.
  • ZIEL=$2 → das Ziel ist der erste Parameter, also $1. Das ist der stille Fehler: keine Meldung, aber $2 ist leer.
  • if [$# -eq 0] → Leerzeichen nach [ und vor ] fehlen, und das ; then am Zeilenende fehlt ganz.
  • ping -c $ZIEL $ANZAHL → vertauscht. -c will die Anzahl direkt dahinter, das Ziel kommt zuletzt.
#!/bin/bash

ANZAHL=3
ZIEL=$1

if [ $# -eq 0 ]; then
    echo "Kein Ziel angegeben"
    exit 1
fi

ping -c $ANZAHL $ZIEL

Warum bash -x hier gewinnt: Es zeigt dir + ping -c google.ch 3 mit eingesetzten Werten. Da springt die Vertauschung sofort ins Auge — und dass $ZIEL leer war, siehst du an + ZIEL=.

05 Container und eigene Images

CLI-Grundlagen, detached mode, Port-Mapping, Dockerfile.

A12

Erster Apache-Container

  • Pullen (noch nicht starten) Sie das httpd Container-Image mit dem Tag 2.4 vom Docker Hub
  • Starten Sie einen Container aus dem Image, benennen Sie ihn apache
    • Listen Sie alle laufenden Container auf
    • Prüfen Sie die Logs des Containers
    • Öffnen Sie eine Shell im laufenden Container und prüfen Sie die Apache-Version via httpd -v
    • Schauen Sie im Container nach, welcher Kernel läuft (uname -r) und vergleichen Sie mit dem Host
  • Stoppen Sie den Container und listen Sie alle Container inkl. der gestoppten auf
  • Entfernen Sie den gestoppten Container und listen Sie alle Images auf
Tipp

Starte gleich mit -d --name apache, dann bleibt dein Terminal frei und du musst keinen Zufallsnamen ablesen.

Für den Container-Namen gilt: apache ist dein Container, httpd:2.4 das Image. In docker logs und docker exec gehört der Container hin.

docker ps zeigt nur laufende. Für die gestoppten brauchst du einen Schalter.

Lösung 
sudo docker pull httpd:2.4

sudo docker run -d --name apache httpd:2.4
sudo docker ps
sudo docker logs apache

sudo docker exec -it apache /bin/bash
#   im Container:
httpd -v
uname -r
exit

sudo docker stop apache
sudo docker ps -a
sudo docker rm apache
sudo docker images

Was du am Kernel siehst: uname -r liefert drinnen genau denselben Kernel wie auf der VM. Der Container bringt nur das Userland mit — das ist der Unterschied zu einer VM.

A13

Detached mit Port-Mapping

  • Starten Sie einen Container mit httpd im detached mode
  • Mappen Sie den Port 80 des Containers auf Port 9090 des Host-Systems
  • Prüfen Sie mit curl, ob die Apache-Startseite erreichbar ist
  • Schauen Sie in docker ps die Spalte PORTS an und erklären Sie, was dort steht
  • Räumen Sie danach auf: stoppen und entfernen
Erwarteter Output
$ curl http://localhost:9090
<html><body><h1>It works!</h1></body></html>
Tipp

Die Reihenfolge beim Mapping ist -p HOST:CONTAINER. Links der Port, den du von aussen ansprichst, rechts der, auf dem der Dienst intern lauscht.

Apache lauscht im Container auf 80 — das steht fest. Welcher Port aussen steht, bestimmst du.

Lösung 
sudo docker run -d --name web -p 9090:80 httpd:2.4

curl http://localhost:9090
sudo docker ps

sudo docker rm -f web

In docker ps steht dann 0.0.0.0:9090->80/tcp: Alles, was auf dem Host an Port 9090 ankommt, wird an Port 80 im Container weitergereicht.

Häufigster Fehler: -p 80:9090 geschrieben. Dann lauscht der Host auf 80 und leitet auf 9090 im Container — wo nichts ist. curl läuft ins Leere.

A14

Eigenes Image bauen

Dockerfile
  • Erstellen Sie ein neues leeres Verzeichnis als Arbeitsverzeichnis für den Container-Build
  • Legen Sie darin eine eigene index.html mit beliebigem Inhalt an
  • Schreiben Sie ein Dockerfile mit folgenden Anforderungen:
    • Basis-Image ist httpd:2.4
    • Ihre index.html wird an die richtige Stelle im Image kopiert
      • Der Pfad beim httpd-Image ist /usr/local/apache2/htdocs/
    • Zusätzlich soll der Port 80 im Image dokumentiert werden
  • Bauen Sie das Image mit dem Tag mein-apache
  • Starten Sie einen Container daraus mit passendem Port-Mapping und prüfen Sie mit curl
  • Löschen Sie den Container, starten Sie einen neuen aus demselben Image und prüfen Sie erneut mit curl
Tipp

Du brauchst drei Instruktionen: eine für das Basis-Image, eine zum Kopieren, eine zum Dokumentieren des Ports. Das Basis-Image bringt sein CMD schon mit — anders als bei debian musst du hier keines setzen.

Der Punkt am Ende von docker build -t name . ist der Build-Context, also das aktuelle Verzeichnis. Den vergisst man gerne.

Die letzte Teilaufgabe ist die eigentliche Frage: Überlebt deine Seite das Löschen des Containers? Überleg dir die Antwort, bevor du es ausprobierst.

Lösung 
mkdir ~/mein-apache && cd ~/mein-apache
nano index.html          # beliebigen HTML-Inhalt schreiben
nano Dockerfile

FROM httpd:2.4

COPY index.html /usr/local/apache2/htdocs/index.html

EXPOSE 80

sudo docker build -t mein-apache .
sudo docker run -d --name web -p 9090:80 mein-apache
curl http://localhost:9090

# Beweis, dass die Seite im Image steckt:
sudo docker rm -f web
sudo docker run -d --name web -p 9090:80 mein-apache
curl http://localhost:9090     # Seite ist immer noch da

Die Antwort auf die Frage: Ja, die Seite überlebt. Sie steckt in einem Image-Layer, nicht im Container. Hättest du die Datei stattdessen mit docker exec im laufenden Container editiert, wäre sie beim rm weg gewesen — die läge nämlich im R/W-Layer.

EXPOSE öffnet keinen Port. Es ist reine Dokumentation im Image. Erreichbar wird der Port erst durch -p beim Starten.

A15

Den R/W-Layer untersuchen

  • Starten Sie einen Container aus dem Image alpine im detached mode mit dem Namen layer-demo, der einen Endlos-Sleep ausführt
  • Führen Sie docker diff aus — die Ausgabe sollte leer sein
  • Erzeugen Sie nacheinander drei verschiedene Deltas im Container:
    • eine neue Datei anlegen: /tmp/notiz.txt
    • eine bestehende Datei ändern: etwas an /etc/hosts anhängen
    • eine bestehende Datei löschen: /etc/motd
  • Führen Sie nach jedem Schritt docker diff aus und beobachten Sie die Präfixe
  • Entfernen Sie den Container, starten Sie einen neuen mit demselben Befehl und führen Sie docker diff erneut aus

Fragen:

  • Welche Ausgabe erwarten Sie beim neuen Container, und warum?
  • Warum erscheint die gelöschte Datei als D und verschwindet nicht einfach?
Tipp

sleep infinity ans Ende des run-Befehls hängen, damit der Container am Leben bleibt.

Einzelne Befehle im Container ausführen geht ohne Shell: docker exec container befehl. Für das Anhängen an eine Datei brauchst du allerdings eine Shell, weil die Umleitung sonst auf dem Host passiert — also sh -c "...".

Die drei Präfixe: A added, C changed, D deleted.

Lösung 
sudo docker run -d --name layer-demo alpine sleep infinity
sudo docker diff layer-demo                 # leer

sudo docker exec layer-demo touch /tmp/notiz.txt
sudo docker diff layer-demo                 # A /tmp/notiz.txt

sudo docker exec layer-demo sh -c 'echo "1.2.3.4 test" >> /etc/hosts'
sudo docker diff layer-demo                 # C /etc/hosts

sudo docker exec layer-demo rm /etc/motd
sudo docker diff layer-demo                 # D /etc/motd

sudo docker rm -f layer-demo
sudo docker run -d --name layer-demo alpine sleep infinity
sudo docker diff layer-demo                 # wieder leer

Antwort 1: Die Ausgabe ist leer. Alle Änderungen lagen im R/W-Layer des alten Containers, und der ist mit ihm gelöscht worden. Der neue Container bekommt eine frische, leere Schicht über denselben unveränderten Image-Layern.

Antwort 2: Die Datei liegt im schreibgeschützten Image-Layer — dort kann physisch nichts gelöscht werden. Docker notiert die Löschung stattdessen als Eintrag in der R/W-Schicht und blendet die Datei nur aus.

Warum sh -c? Bei docker exec container echo x >> /etc/hosts wertet deine Host-Shell die Umleitung aus — du würdest in die /etc/hosts der VM schreiben. Mit sh -c "..." passiert alles im Container.

A16

PostgreSQL mit Volume und Bind Mount

Zielsetzung: Die Datenbankdateien sollen in einem Docker Volume liegen, das Init-Skript wird über einen Bind Mount eingebunden.

  • Erstellen Sie ein Named Volume namens pg-data und listen Sie alle Volumes auf
  • Erstellen Sie einen Ordner auf dem Host mit einer Datei init.sql, die eine Tabelle anlegt und drei Zeilen einfügt
  • Starten Sie postgres:17 mit zwei Volume-Flags:
    • das Named Volume für die Datenbankdateien (Pfad steht im README des Images auf Docker Hub)
    • einen Bind Mount auf Ihren Ordner mit dem Skript
  • Das Image braucht zusätzlich die Umgebungsvariable POSTGRES_PASSWORD — nutzen Sie dafür das Flag -e
  • Laden Sie die Daten mit psql und prüfen Sie mit einer Abfrage, dass sie da sind
  • Löschen Sie den Container, starten Sie einen neuen mit denselben Mounts und prüfen Sie erneut
Tipp

Der Datenpfad von Postgres ist /var/lib/postgresql/data.

Named Volume und Bind Mount benutzen dasselbe Flag -v, unterscheiden sich aber links vom Doppelpunkt: ein Name → Volume, ein Pfad → Bind Mount.

Postgres braucht ein paar Sekunden zum Hochfahren. Wenn psql meckert, kurz warten und nochmal.

Ein Befehl in psql ohne interaktive Sitzung: psql -U postgres -c "SELECT ...".

Lösung 
sudo docker volume create pg-data
sudo docker volume ls

mkdir ~/pg-init
nano ~/pg-init/init.sql

CREATE TABLE kurse (id INT, name TEXT);
INSERT INTO kurse VALUES (1,'INSY'), (2,'EidI'), (3,'MGLI');

sudo docker run -d --name pg \
  -e POSTGRES_PASSWORD=geheim \
  -v pg-data:/var/lib/postgresql/data \
  -v ~/pg-init:/initscripts \
  postgres:17

# kurz warten, dann Daten laden
sudo docker exec -it pg psql -U postgres -f /initscripts/init.sql
sudo docker exec -it pg psql -U postgres -c "SELECT * FROM kurse;"

# Container weg, neuer Container, gleiche Mounts
sudo docker rm -f pg
sudo docker run -d --name pg \
  -e POSTGRES_PASSWORD=geheim \
  -v pg-data:/var/lib/postgresql/data \
  -v ~/pg-init:/initscripts \
  postgres:17

sudo docker exec -it pg psql -U postgres -c "SELECT * FROM kurse;"
# → die drei Zeilen sind noch da

Warum es funktioniert: Die Datenbankdateien lagen nie im Container, sondern im Volume pg-data. Das gehört Docker, nicht dem Container — und überlebt ihn deshalb.

Aufräumen mit Vorsicht: docker rm pg lässt das Volume stehen. Erst docker volume rm pg-data oder docker system prune --volumes löscht die Daten wirklich.

A17

Zwei getrennte Netzwerke

  • Erstellen Sie zwei Custom Bridge Networks namens shop_app_net und shop_db_net
  • Inspizieren Sie beide Netzwerke und notieren Sie die jeweiligen Subnetze
  • Starten Sie zwei Container im shop_app_net: shop_app1 und shop_app2, Image busybox, Befehl sleep infinity
  • Starten Sie zwei Container im shop_db_net: shop_db1 und shop_db2, gleiches Image und gleicher Befehl
  • Prüfen Sie die Erreichbarkeit innerhalb jedes Netzwerks mit ping -c 3
  • Prüfen Sie die Isolation zwischen den Netzwerken
  • Inspizieren Sie beide Netzwerke erneut und prüfen Sie, dass jeweils nur die eigenen Container im Containers-Abschnitt stehen

Zusatzfrage: Was fällt Ihnen an den IP-Adressen der vier Container auf?

Tipp

Beim run-Befehl bestimmt das Flag --network, in welchem Netz der Container landet.

Die Fehlermeldung beim netzübergreifenden Ping ist aufschlussreich — lies sie genau. Sie sagt nicht „keine Antwort".

Bei docker network inspect sind zwei Abschnitte interessant: Containers und IPAM → Config → Subnet.

Lösung 
sudo docker network create shop_app_net
sudo docker network create shop_db_net
sudo docker network inspect shop_app_net

sudo docker run -d --name shop_app1 --network shop_app_net busybox sleep infinity
sudo docker run -d --name shop_app2 --network shop_app_net busybox sleep infinity
sudo docker run -d --name shop_db1  --network shop_db_net  busybox sleep infinity
sudo docker run -d --name shop_db2  --network shop_db_net  busybox sleep infinity

sudo docker exec -it shop_app1 ping -c 3 shop_app2    # geht
sudo docker exec -it shop_db1  ping -c 3 shop_db2     # geht
sudo docker exec -it shop_app1 ping -c 3 shop_db1     # bad address

sudo docker network inspect shop_app_net
sudo docker network inspect shop_db_net

Zur Zusatzfrage: Beide Netze vergeben .0.2 und .0.3 — es gibt also zweimal dieselbe Endung auf einer Maschine. Kein Konflikt, weil die Subnetze verschieden sind (z. B. 172.18.0.0/16 und 172.19.0.0/16) und keine Route dazwischen existiert.

Warum bad address und nicht „timeout": Docker betreibt pro Netz einen kleinen DNS. Der kennt nur die Container des eigenen Netzes. Für shop_app1 existiert der Name shop_db1 gar nicht — es scheitert schon an der Namensauflösung, nicht erst am Paket.

A18

Dasselbe mit Compose

docker-compose.yml
  • Räumen Sie zuerst die Container und Netze aus A17 auf
  • Erstellen Sie ein neues leeres Verzeichnis für Ihre docker-compose.yml
  • Bilden Sie das Setup aus A17 mit Docker Compose nach:
    • zwei Container shop_app1 und shop_app2 im Netzwerk shop_app_net
    • zwei Container shop_db1 und shop_db2 im Netzwerk shop_db_net
  • Prüfen Sie die Datei vor dem Start mit docker compose config
  • Starten Sie alles mit einem Befehl und wiederholen Sie die Ping-Tests aus A17
  • Räumen Sie mit einem Befehl wieder auf

Frage: Vergleichen Sie docker network ls mit den Namen aus Ihrer YAML-Datei. Was fällt auf, und warum macht Compose das?

Tipp

Eine Compose-Datei hat zwei Hauptteile auf oberster Ebene: services: und networks:.

Jeder Service braucht vier Angaben: image, container_name, command und networks. Die vier Blöcke sind bis auf Name und Netz identisch.

Die Wörter links vom Doppelpunkt sind feste Schlüsselwörter — nur die Werte rechts davon setzt du selber.

YAML kennt keine Tabs. Zwei Leerzeichen pro Ebene, und die Einrückung ist die Struktur.

Ein Netz, das du unter einem Service nennst, muss auch im unteren networks:-Block stehen — sonst refers to undefined network.

Lösung 
sudo docker rm -f shop_app1 shop_app2 shop_db1 shop_db2
sudo docker network rm shop_app_net shop_db_net

mkdir ~/shop-compose && cd ~/shop-compose
nano docker-compose.yml

services:
  shop_app1:
    image: busybox
    container_name: shop_app1
    command: sleep infinity
    networks:
      - shop_app_net

  shop_app2:
    image: busybox
    container_name: shop_app2
    command: sleep infinity
    networks:
      - shop_app_net

  shop_db1:
    image: busybox
    container_name: shop_db1
    command: sleep infinity
    networks:
      - shop_db_net

  shop_db2:
    image: busybox
    container_name: shop_db2
    command: sleep infinity
    networks:
      - shop_db_net

networks:
  shop_app_net:
  shop_db_net:

sudo docker compose config          # prüfen
sudo docker compose up -d           # starten
sudo docker ps
sudo docker network ls

sudo docker exec -it shop_app1 ping -c 3 shop_app2    # geht
sudo docker exec -it shop_app1 ping -c 3 shop_db1     # geht nicht

sudo docker compose down            # alles weg

Zur Frage: Die Netze heissen shop-compose_shop_app_net statt nur shop_app_net. Compose nimmt den Ordnernamen als Projektnamen und hängt ihn vorne an alles, was es anlegt. So können zwei Projekte beide ein Netz namens backend haben, ohne sich zu stören. Die Container behalten ihren Namen, weil container_name: gesetzt ist.

Der Gewinn: In A17 waren es zehn Befehle zum Aufbauen und sechs zum Abräumen. Hier ist es eine Datei und zwei Befehle — und die Datei kannst du versionieren, weitergeben und morgen wieder genauso starten. Das ist der Unterschied zwischen imperativ und deklarativ.
